# Mini Swiggy V2 — Core Ordering Protocol Reference

> **Version 2 introduces core food ordering, price snapshots, atomic database transactions, and simulated payment to Mini Swiggy.**  
> Communication continues over the robust newline-delimited JSON (NDJSON) framing on raw TCP sockets established in V1.

---

## 1. Framing and Transport

All communication occurs over a standard TCP connection (default `127.0.0.1:5000`).

- **Framing**: Newline-delimited JSON (NDJSON). Every request and response is a single line of UTF-8 text terminated by `\n` (`0x0A`).
- **Buffers**: Receivers accumulate bytes across `recv()` calls until `\n` is encountered.
- **Max Message Size**: 64 KiB (65,536 bytes). Messages exceeding this trigger `MESSAGE_TOO_LARGE` and close the connection.
- **Connection Model**: Sequential client processing in V2 (concurrency and worker pools scheduled for V3). Multiple requests may be sent sequentially over a single open connection.

## 2. Request & Response Envelopes

### Request Envelope
```json
{
  "request_id": "req-001",
  "action":     "create_order",
  "payload":    { ... }
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `request_id` | string | Yes | Unique identifier generated by client, echoed in response |
| `action` | string | Yes | Name of the action to invoke |
| `payload` | object | Yes | Action-specific parameters |

### Success Response Envelope
```json
{
  "request_id": "req-001",
  "ok":         true,
  "data":       { ... }
}
```

### Error Response Envelope
```json
{
  "request_id": "req-001",
  "ok":         false,
  "error": {
    "code":    "INVALID_PAYLOAD",
    "message": "Order cart cannot be empty. Must include at least one item."
  }
}
```

### 3.4 `create_order` (V2 Core)
Places a new food order with item snapshots and server-side price calculation.

#### Security & Integrity Rules:
1. **Never trust client prices**: Any `price` field provided in the client payload is ignored. The server retrieves official prices from SQLite `menu_items`.
2. **Atomic transaction**: The order header and all line items are inserted inside a single SQLite transaction. If any insert or constraint fails, the entire transaction rolls back cleanly.
3. **Price snapshotting**: The unit price is saved in `order_items.unit_price` at the moment of ordering, preserving historical accuracy if the restaurant later updates menu prices.
4. **Validation**: Rejects empty carts, negative or non-integer quantities, non-existent users, closed restaurants, unavailable items, and items belonging to a different restaurant.

- **Request**:
  ```json
  {
    "request_id": "r4",
    "action": "create_order",
    "payload": {
      "customer_id": 1,
      "restaurant_id": 1,
      "items": [
        {"item_id": 1, "quantity": 2},
        {"item_id": 2, "quantity": 1}
      ]
    }
  }
  ```
- **Response**:
  ```json
  {
    "request_id": "r4",
    "ok": true,
    "data": {
      "order_id": 1,
      "customer_id": 1,
      "restaurant_id": 1,
      "restaurant_name": "Hyderabad Spice House",
      "total_amount": 480.0,
      "order_status": "placed",
      "payment_status": "pending",
      "items": [
        {
          "item_id": 1,
          "name": "Chicken Biryani",
          "quantity": 2,
          "unit_price": 180.0,
          "subtotal": 360.0
        },
        {
          "item_id": 2,
          "name": "Veg Biryani",
          "quantity": 1,
          "unit_price": 120.0,
          "subtotal": 120.0
        }
      ]
    }
  }
  ```

### 3.5 `simulate_payment` (V2 Core)
Simulates payment processing and records the outcome in SQLite.

#### Rules:
1. **Idempotent duplicate prevention**: If an order has already been marked as `paid`, any repeated payment request is rejected with `PAYMENT_ALREADY_COMPLETED`.
2. **Controlled simulation**: The client can simulate success (default or `simulate_status: "paid"`) or failure (`simulate_status: "failed"` or `simulate_failure: true`).
3. **Failure handling**: A failed payment does NOT mark the order as paid; `order_status` remains `placed` and `payment_status` becomes `failed`. The customer may retry.
4. **Success handling**: On success, `payment_status` becomes `paid` and `order_status` transitions to `accepted`. A unique transaction reference (`TXN-SIM-...`) is recorded in the `payments` table.

- **Request (Success)**:
  ```json
  {
    "request_id": "r5",
    "action": "simulate_payment",
    "payload": {
      "order_id": 1,
      "payment_method": "upi",
      "simulate_status": "paid"
    }
  }
  ```
- **Response (Success)**:
  ```json
  {
    "request_id": "r5",
    "ok": true,
    "data": {
      "payment_id": 1,
      "order_id": 1,
      "amount": 480.0,
      "payment_status": "paid",
      "order_status": "accepted",
      "transaction_ref": "TXN-SIM-1-4A7B1C8D",
      "payment_method": "upi"
    }
  }
  ```

- **Request (Failure Simulation)**:
  ```json
  {
    "request_id": "r5-fail",
    "action": "simulate_payment",
    "payload": {
      "order_id": 1,
      "simulate_status": "failed"
    }
  }
  ```
- **Response (Failure Simulation)**:
  ```json
  {
    "request_id": "r5-fail",
    "ok": true,
    "data": {
      "payment_id": 1,
      "order_id": 1,
      "amount": 480.0,
      "payment_status": "failed",
      "order_status": "placed",
      "transaction_ref": "TXN-SIM-1-9F2D8E4C",
      "payment_method": "simulated_upi"
    }
  }
  ```

## 4. State Machines

### Order Status Lifecycle
```
[ placed ] ──── (successful payment) ────> [ accepted ] ────> [ preparing ] ────> [ ready ] ────> [ out_for_delivery ] ────> [ delivered ]
    │
    └─────────── (cancelled) ───────────> [ cancelled ]
```

### Payment Status Lifecycle
```
[ pending ] ──┬── (simulate success) ──> [ paid ] (terminal for payment, repeated charges blocked)
              └── (simulate failure) ──> [ failed ] (retry permitted)
```

## 5. Error Codes

| Code | HTTP Equivalent | When returned |
|---|---|---|
| `UNKNOWN_ACTION` | 404 Not Found | Action name is not in the dispatch table |
| `INVALID_REQUEST` | 400 Bad Request | Action is missing, non-string, or business logic violated (e.g. paying for cancelled order, item from wrong restaurant) |
| `INVALID_PAYLOAD` | 422 Unprocessable | Field missing, wrong data type (e.g. string for integer ID), empty cart, or negative quantity |
| `NOT_FOUND` | 404 Not Found | Referenced entity (user, restaurant, menu item, or order) does not exist |
| `ITEM_UNAVAILABLE` | 409 Conflict | Menu item has `is_available = 0` |
| `RESTAURANT_CLOSED` | 409 Conflict | Restaurant has `is_open = 0` |
| `PAYMENT_ALREADY_COMPLETED` | 409 Conflict | Attempting to pay for an order that is already marked `paid` |
| `DB_ERROR` | 500 Server Error | SQLite database error (raw internal error details hidden from client) |
| `MALFORMED_JSON` | 400 Bad Request | Incoming line is not valid JSON |
| `MESSAGE_TOO_LARGE` | 413 Payload Too Large | Inbound message exceeded 64 KiB buffer without `\n` |

## 6. V2 Architectural Scope and Limitations

Mini Swiggy V2 implements core food ordering over pure TCP sockets and SQLite.

### What V2 Is:
- A functional TCP client-server ordering platform with atomic transactions, price snapshots, and idempotent payment tracking.
- An educational tool demonstrating low-level socket protocol design, message framing, database consistency, and defensive validation.

### What V2 Is NOT:
- **Not concurrent yet**: The server remains single-threaded, processing clients sequentially. Concurrency (multithreading / asyncio) is scheduled for V3.
- **Not a distributed production replica**: There are no message brokers (Kafka/RabbitMQ), distributed caches (Redis), microservices, API gateways, or container orchestration (Docker/Kubernetes).
- **Not a real payment gateway**: Payments are simulated locally. No real banking credentials or external webhooks are integrated.
